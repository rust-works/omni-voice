# ADR-0038: Async `StreamingTranscriber` Seam Alongside the Sync `Transcriber`

## Status

✅ Accepted (2026-06-21) — extends [ADR-0032](adr-0032.md) (the synchronous
`AudioInput`/`Transcriber` seam) additively; prerequisite for the
streaming-native backends selected in [ADR-0042](adr-0042.md).
[ADR-0040](adr-0040.md) reserved this slot for the async seam. First consumer is
the Parakeet incremental streaming backend
([#24](https://github.com/rust-works/omni-voice/issues/24)) under the Phase-3
epic ([#44](https://github.com/rust-works/omni-voice/issues/44)).

## Context

[ADR-0032](adr-0032.md) established the **synchronous** transcription seam on
`main`: `AudioInput: Send` (`fn next_chunk(&mut self) -> Option<AudioChunk>`)
feeding `Transcriber::transcribe(&self, Box<dyn AudioInput>) -> Result<Box<dyn
EventStream>>`, where `EventStream` is a blanket-impl'd synchronous
`Iterator<Item = Result<TranscriptEvent>> + Send`. The batch backends (candle
Whisper, `mock`) are built on it, and it is sufficient for "decode a whole WAV
or pre-buffered input".

Streaming-native ASR differs in kind, not degree. A streaming backend
([ADR-0042](adr-0042.md) selects streaming-native MLX as the headline tier and
keeps parakeet-candle as a live option) must:

- **pull audio as it arrives** from a live source — a `cpal` capture channel, a
  network socket, or a paced file feeder — where the next chunk may not be ready
  yet. A synchronous `next_chunk` that blocks the calling thread until the next
  chunk arrives cannot share an async executor with the rest of the pipeline
  without dedicating a thread per stream.
- **emit events incrementally** — `Partial { revisable: true }` mid-utterance,
  `Final` + `Endpoint` at silence gaps — interleaved with audio arrival, rather
  than returning a fully-formed iterator only after the input is drained.

Three options were considered:

1. **Make the existing `Transcriber`/`AudioInput` seam async.** This forces every
   batch backend and every batch call site (`transcribe`, the fixture tests)
   onto `async fn` and an executor they do not need, and churns ADR-0032's
   shipped contract. Rejected: batch transcription has no reason to be async, and
   the sync seam is load-bearing on `main`.
2. **Reuse the sync seam for streaming**, driving `next_chunk` on a blocking
   thread and bridging to the event consumer through a channel. It works, but
   pushes every backend to own its own thread-plus-channel plumbing, and the
   blocking `next_chunk` cannot represent "await the next chunk from the
   executor" — exactly the property live capture and network sources need.
   Rejected: it re-introduces the `!Send`/thread-bridging problem ADR-0032
   deliberately confined to a single adapter.
3. **Add a separate, additive async seam** — `AsyncAudioInput` +
   `StreamingTranscriber` — alongside the sync one, reusing the same
   `TranscriptEvent` vocabulary. Batch backends keep the sync seam untouched;
   streaming backends implement the async one. This mirrors ADR-0032's own "two
   seams for two boundaries" reasoning (capture-side `AudioSource` versus
   ASR-side `AudioInput`).

## Decision

We will add an **additive async seam** for streaming transcription, leaving the
synchronous ADR-0032 seam unchanged.

```rust
#[async_trait]
pub trait AsyncAudioInput: Send {
    async fn next_chunk(&mut self) -> Option<AudioChunk>;
}

pub trait StreamingTranscriber: Send + Sync {
    fn transcribe_stream(
        &self,
        audio: Box<dyn AsyncAudioInput>,
    ) -> Pin<Box<dyn Stream<Item = Result<TranscriptEvent>> + Send>>;
}
```

- **`AsyncAudioInput` is the async counterpart of `AudioInput`** — same
  `AudioChunk = Vec<i16>` (16 kHz mono) contract, same chunk-boundary semantics,
  same `Send` bound — differing only in that `next_chunk` is `async`, so a call
  site can `await` next-chunk delivery without blocking the executor. We use
  `async-trait` for the `async fn` in a `dyn`-dispatched trait; the per-call
  boxing cost is negligible against per-chunk inference.
- **`StreamingTranscriber::transcribe_stream` returns `Pin<Box<dyn Stream<…> +
  Send>>`** (futures 0.3). A pinned boxed `Stream` is object-safe, lets each
  backend pick its own stream implementation (a hand-rolled `Stream`,
  `stream::unfold`, or the `async_stream` macro) without leaking that choice into
  the trait, and is `Send` so the stream can move across tasks and threads. The
  stream completes when the input is drained; backends emit a terminal
  `Endpoint { kind: StreamEnd, .. }` before completing.
- **The event vocabulary is shared.** `transcribe_stream` yields the same
  `TranscriptEvent` (`Partial`/`Final`/`Endpoint`) as the sync seam, so
  downstream consumers (reflection, reconciliation) do not fork by seam.
  `Partial` and the revisable `Final` flag were already designed into
  `TranscriptEvent` for exactly this path.
- **`Send + Sync` on the trait matches `Transcriber`.** Per-session mutable state
  (LSTM hidden state, encoder KV caches, running normalisation statistics) lives
  behind a `Mutex` or a per-stream owner inside the backend, not on the trait.
- **`FileAsyncAudioInput` ships as the WAV-as-live test driver** — the async
  counterpart of `VecAudioInput`, yielding a 16 kHz mono i16 WAV (or in-memory
  `Vec<i16>`) in fixed-size chunks. v1 yields without realtime pacing;
  realtime/paced feeding (for first-partial-latency measurement) is a thin
  follow-up on the same type. WAV-shape validation is shared with `VecAudioInput`
  through a single `load_16k_mono_i16_wav` helper so the two inputs cannot drift.

This adds two top-level dependencies — `async-trait = "0.1"` and
`futures = "0.3"` — which compose with the `tokio` runtime already in tree.

## Consequences

### Positive

- Streaming backends get a seam that models live audio honestly: `await`-able
  chunk pulls and an incremental event `Stream`, composable with `StreamExt` and
  any `tokio` source, with no thread-per-stream bridging.
- The shipped synchronous batch seam (ADR-0032) is untouched — the change is
  additive, with zero churn to batch backends or their snapshot tests.
- Reusing `TranscriptEvent` keeps one event vocabulary across batch and
  streaming; downstream reflection and reconciliation consume both without a
  fork.
- The shared `load_16k_mono_i16_wav` helper removes the WAV-validation
  duplication the two `from_wav_path` constructors would otherwise carry.

### Negative

- Two transcription seams now coexist (sync `Transcriber`, async
  `StreamingTranscriber`); contributors must pick the right one for their layer.
  Mitigated by tight docstrings and this ADR.
- Two new dependencies (`async-trait`, `futures`). `async-trait`'s per-call
  allocation is a real (if here-negligible) cost, and `futures` widens the
  dependency surface — both are mainstream and already transitively present via
  the `tokio` ecosystem.

### Neutral

- The seam is the contract only; concrete streaming algorithms live in backends.
  The Parakeet incremental streaming backend
  ([#24](https://github.com/rust-works/omni-voice/issues/24)) is the first
  consumer, and the streaming-native MLX subprocess
  ([ADR-0042](adr-0042.md)) targets the same trait — making
  `transcribe_stream` the seam at which the Phase-3
  ([#44](https://github.com/rust-works/omni-voice/issues/44)) A-versus-B decision
  is measured.
- The `MixdownResampleAudioInput<S: AudioSource>` adapter that bridges live
  `cpal` capture (`!Send`, f32, variable-rate) into an `AsyncAudioInput` remains
  future work (already foreshadowed by ADR-0032); `FileAsyncAudioInput` covers
  fixture-driven measurement until it lands.
- `FileAsyncAudioInput`'s realtime pacing is deferred: the unpaced driver is
  sufficient for correctness and WER, and paced feeding is added when
  first-partial latency is measured for the #44 decision.
